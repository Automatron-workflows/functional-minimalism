# Launch Functional Minimalism

The useful promise is **Better UI. Fewer retries.** The primary experiment is to choose a real screen, inspect a compact brief, carry one accepted correction into another screen, and use the installed starter with a coding agent.

Stars are a distribution outcome. The initial goal is ten developers completing setup and five sharing reproducible builds. These are launch targets, not current results. Thousands of stars remains a stretch outcome; no campaign can ensure it.

## Release gate

Before public promotion:

- Push the reviewed commits to Automatron-workflows/functional-minimalism.
- Require the Pages workflow to pass all unit, source, build, and actual-width browser checks.
- Open the deployed URL on desktop and phone; exercise playback, Why, Set up, workshop, Get screen brief, memory, and downloads.
- Use the downloaded source archive for setup and doctor, not only a development checkout.
- Publish an accurate verification record and a working source link. npm publication is not a launch dependency; do not advertise an npm install command before a verified release exists.

## Fourteen days from verified publication

| Days 5–7 | Prepare a founder post and a technical community submission linking directly to the useful experiment. Publish only with explicit channel authorization. | Visits available in provider statistics, voluntary completed-run reports, GitHub traffic and stars. |

| Days 11–14 | Ship the most repeated improvement and publish the comparison results, including regressions. | Returning contributors, issue resolution, successful first builds, and stars gained. |

No bought stars, engagement exchanges, unsolicited bulk messages, or fabricated testimonials. Ask for a star after someone gets useful value. Keep issues and contributions easy to find. Do not add invasive telemetry to the demo; it currently makes no analytics calls.

## Draft founder post

I kept giving coding agents the same design feedback: fewer explanations, clearer hierarchy, show the useful object first.

So I built Functional Minimalism: a small, dependency-free harness that puts your design system, the person's task, and accepted decisions into the next screen brief.

Inspired by Dieter Rams. Built around function, clarity, and restraint. Useful labels, prices, permissions, and recovery stay visible.

Try one screen: choose discovery, invoice review, or project tasks. Take its brief into your coding agent. Then compare the result under the same acceptance criteria.

The goal is better first drafts with less time and fewer tokens spent correcting them. I haven't measured a general saving yet. I'd like reproducible examples that prove where it helps and where it doesn't.

## Draft technical submission

Title: Show HN: Functional Minimalism, reusable design judgment for coding agents

I built a local design harness for a recurring problem: AI-generated interfaces often add explanations and decorative structure before solving the person's task.

This project supplies versioned component maps, a small screen contract, scoped accepted decisions, and deterministic source/rendered-evidence checks. Your agent still performs the design and browser work. The demo is an authored illustration; the workshop runs real local interactions and checks.

No model calls, account, API key, or npm dependencies are needed to inspect the harness. The source setup supports Codex and Claude instruction files. Other agents can read the generated brief.

I'm looking for feedback on one experiment: build the same invoice review task with and without the harness, retain recipient/amount/destination/confirmation, and compare corrections, elapsed time, and actual token usage. Raw results matter more than a good-looking screenshot.
